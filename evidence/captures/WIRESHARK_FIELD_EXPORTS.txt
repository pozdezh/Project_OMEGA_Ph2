## FINDINGS (read first)

1. BOTH paths negotiate DTLS 1.3. supported_versions extension = 0xfefc (DTLS 1.3)
   in every ServerHello and HelloRetryRequest. Zero packets select 0xfefd (1.2).
   The 'DTLS 1.2 (0xfefd)' in the record/legacy_version field is frozen by RFC 9147
   and Wireshark's own expert info says to ignore it.

2. A HelloRetryRequest is present on BOTH paths (Random = the RFC 8446 HRR magic
   cf21ad74...c8a8339c). HRR exists only in (D)TLS 1.3. It also carries a cookie
   extension = the RFC 9147 return-routability / anti-DoS check, on real hardware.

3. Cipher suite, read from the ServerHello:
     AMU_16 <-> server : TLS_AES_256_GCM_SHA384 (0x1302)
     NMU_T1 <-> server : TLS_AES_128_GCM_SHA256 (0x1301)

4. Key-exchange group, read from key_share (ServerHello) and supported_groups (ClientHello):
     AMU_16 <-> server : SecP384r1MLKEM1024 (0x11ed)  ==  HYBRID post-quantum
                         (NIST P-384 ECDHE + ML-KEM-1024 / FIPS 203). Not configured
                         anywhere in the project - it is the wolfSSL 5.9.2 default,
                         offered by the AMU and selected by the server.
     NMU_T1 <-> server : secp256r1 (0x17)             ==  classical P-256 ECDHE.
                         The Arduino wolfSSL 5.8.4 build offers only
                         secp521/384/256/224 - no MLKEM groups.
   => 'P-256 ECDHE everywhere' is WRONG. The AMU link is already PQ-hybrid.
      Certificates are still P-256 ECDSA on both (omega_pki.py CURVE=SECP256R1;
      AMU ClientHello signature_algorithms include ecdsa_secp256r1_sha256).

5. NMU ClientHello offers 0x1301 but NOT 0x1302/0x1303 - its trimmed build has no
   SHA-384, so it cannot even propose AES-256. AMU offers 0x1302,0x1301,0x1303.
