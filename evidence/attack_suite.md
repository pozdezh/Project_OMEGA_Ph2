## How to read this, and what it does not prove

Every attack below runs against a complete copy of the shipped server code, over a real mutual-authentication handshake, inside a throwaway directory with its own certificate authority and its own database. The devices are invented (`AMU_01`, `NMU_01`); no deployed unit, key or measurement is involved, so nothing here can leak an unmeasured number into the project's real data.

**The channel here is DTLS 1.2, not 1.3.** OpenSSL on the development machine predates DTLS 1.3, and wolfSSL has no Windows build. What is proven here is therefore version-independent: mutual authentication, forward secrecy, certificate-bound identity, refusal of an unknown authority, revocation, and detection of an altered record. **DTLS 1.3 itself is proven only on hardware**, where the live server and the ESP32 both report `DTLSv1.3 / TLS_AES_128_GCM_SHA256`.

## 2. A genuine device lying about which unit it is

**The attacker has:** a valid certificate for AMU_01 and its private key

**What was attempted:** send a record claiming `"id": "NMU_99"` so the reading is filed against a different unit

**What happened:** The lie is ignored. Identity is taken from the certificate the device authenticated with, never from the message body.

**Evidence**

```
claimed in the record : NMU_99
certificate presented : AMU_01
stored under          : AMU_01
```

## 3. Replaying a captured record

**The attacker has:** a recorded copy of an earlier, perfectly valid record

**What was attempted:** send the identical record again to inflate the readings

**What happened:** The duplicate is absorbed. The database keeps one row per (device, event), so a replay changes nothing.

**Evidence**

```
record sent twice     : event 500_1
rows now in database  : 1
```

## 4. Man in the middle altering a record in flight

**The attacker has:** a position on the shared WLAN allowing bytes to be rewritten as they pass

**What was attempted:** flip a single bit in the encrypted record so the server stores a different value than the device sent

**What happened:** The altered record is discarded and never reaches the application. One bit is enough to invalidate the whole record.

## 5. A rogue device with a certificate from another authority

**The attacker has:** the WLAN password, the server's address, and a certificate it issued to itself

**What was attempted:** complete the handshake and start submitting readings

**What happened:** The handshake never completes. The certificate is not signed by this fleet's authority, so the session is refused before any application data can be sent.

**Evidence**

```
handshake result : HandshakeError: server handshake failed, SSL_get_error=1
```

---

## 6. A rogue operator calling a device directly

**The attacker has:** network access to the device and a self-issued operator certificate

**What was attempted:** open the device's live-query channel and command it directly, bypassing the server

**What happened:** The device refuses the caller. A unit authenticates whoever calls it by certificate, exactly as the server does.

**Evidence**

```
handshake result : HandshakeError: server handshake failed, SSL_get_error=1
```

---

## 7. A retired or stolen unit still holding a valid certificate

**The attacker has:** a genuine, unexpired certificate issued by this fleet's own authority, and its private key

**What was attempted:** reconnect after being retired and continue submitting readings

**What happened:** The unit is refused by name. Revocation does not need the certificate to expire or be recalled from the device.

**Evidence**

```
active unit AMU_01  allowed : True
revoked unit AMU_09 allowed : False
```
